# QFRemote 友聊（二期）设计与实现说明

> 口径：消息加密构造沿 A 案（端到端加解密）；**钥匙托管口径已于 2026-10-25 按站长令修订为「登录状态托管静默解锁」，见第十节——该节覆盖前文一切与实现不符的旧表述（如「站长也看不见内容」「私钥永不出端」「输密码解锁/例外解锁」）。** 方案正本 `../../friends-plan.md` 第六节。
> 状态：模块已实现并本地全链自测通过；2026-10-24 已按合并契约合入东京服务器的 `qfremote-friends` 同一进程上线，生产真测 20/20 通过（见 `../README.md` 的「二期合入上线」）。

## 一、加密模型（全部 libsodium 成熟构造，不自造算法）

依赖 **libsodium-wrappers-sumo**（注意：标准版 `libsodium-wrappers` 不含 `crypto_pwhash`，密码派生必须用 sumo 版——已实测踩坑并写死在代码注释里）。

| 环节 | 构造 | 说明 |
|---|---|---|
| 身份密钥 | X25519 密钥对 `crypto_box_keypair` | 公钥上服务器当目录；私钥原件永不出端 |
| 密码派生 | `crypto_pwhash`（Argon2id13，interactive 参数） | 登录密码＋随机 salt → 「包装钥匙」 |
| 钥匙保管 | `crypto_secretbox`（XSalsa20-Poly1305） | 私钥、保险库钥匙分别被包装钥匙加密成密文包存服务器；服务器没有包装钥匙，解不开 |
| 消息加密 | `crypto_box`（X25519＋XSalsa20-Poly1305），每条随机 nonce | 会话钥匙＝双方私钥×对方公钥的 ECDH 共享钥匙，两端算得同一把 |
| 记录保险库 | 每人一把随机保险库钥匙，`crypto_secretbox` 加密每条记录 | 记录密文上云跟账号走；新端登录→密码解开钥匙包→取回保险库钥匙→历史自动加载 |
| 安全码 | 公钥 generichash 指纹 | 已备函数（三期当面核对用） |

**如实标注的取舍**：会话钥匙是静态 ECDH，没有 QFClash（Signal 双棘轮）的逐条前向保密；本期按方案「参照 QFClash 的中继形态＋成熟算法库＋不自造算法」的铁律落地，构造全是 NaCl 经典组合。若日后要升到 Signal 级双棘轮，属三期工程，数据层（密文行＋保险库）可平移。

**A 案固有代价（已在页面大白话明示，不藏）**：
- 密码被站长重置 → 新密码派生不出旧包装钥匙 → 私钥与历史记录一并作废。登录页与恢复页都写明。
- 记得旧密码的用户自改密码 → 恢复流程可用旧密码解开、换新包装（rewrap），记录不丢（已实测）。
- 私聊内容服务端零明文 → 无法内容审核，处置只能到封号级（与方案一致）。

## 二、数据设计（服务端只有密文与序号）

`chat-data.json`（单文件 JSON、tmp＋rename 原子落盘，与 register-svc 同款）：

- `keys[user]`：`{pub, wrappedPriv{密文包}, wrappedVault{密文包}, updatedAt}`——公钥明文（本就是公开材料），其余全密文。
- `messages[id]`：`{id, from, to, conv, at, nonce, cipher}`——传送正本，只有密文。
- `vault[user][]`：`{msgId, conv, with, dir, at, nonce, cipher}`——各人自己的记录副本，只有本人会话能取、只有本人保险库钥匙能解。
- `events[]` ＋ `eventSeq`：增量拉取流（msg 事件带密文行、tomb 墓碑事件带被删 id 与双方名单），只保留最近 5000 条；历史正本是保险库，不受截断影响。
- `graveyard[id]`：已删消息的 `{from,to,conv,at}` 骨架（无密文），仅供保险库补写校验。
- `readMarks[conv][user]`：已读到的事件序号——只有序号，没有内容。
- `sessions[tokenHash]`：`{user, exp}`，令牌只存 SHA-256，12 小时过期。

删除语义（方案定版）：删一条/删整个对话 → 传送行删、**双方**保险库条目删、墓碑事件广播，各端收到即清本地显示；页面删除确认框明示「软件之外的副本（如截图）删不掉」。

好友闸口：发送时实时查 `friends-gate.js`（`areFriends`）；非好友 403，删好友即刻停发。记录在删好友后保留（属双方各自数据，与 QFClash 口径一致）。

## 三、登录验密（走官方控制通道，不自建密码校验）

聊天页用同一账号＋密码登录：服务端以**用户自己的凭据**开 MeshCentral `control.ashx` 连接验真后发自家会话令牌；密码只过内存，不落盘、不进日志。

行为基准（本机 MeshCentral 1.3.1 测试实例＋源码双证，`probe-auth.js` 存档）：
- 源码 `meshuser.js:667`：认证成功后服务器主动下发 `{action:'userinfo', userinfo:{…}}`；
- 实测：密码正确 → 收到 userinfo ✔；密码错误 → 连接打开后立即被关（1006）、无 userinfo；账号不存在 → 同上。
- 判定写死为：**收到 userinfo 才算验真成功**，error/close/超时一律失败（不能只看 WS open——错密码也会先 open 再被踢）。

## 四、接口表面（全部；没有任何管理端点）

```
GET  /chat  /chat/crypto-core.js  /chat/chat-client.js  /chat/libsodium-wrappers.js  /chat/health
POST /chat/api/login | keys/setup | keys/rewrap | send | vault | read | delete | delete-conversation
GET  /chat/api/friends | support-faq | keys/me | keys/:user | poll | vault | conversations
```
没有任何能返回用户聊天内容的端点——用户内容只以密文经过；`support-faq` 只返回产品预置的固定客服文案。站长能接触到的只有：数据文件（全密文，已抽查）与日志（只记账号名与事件计数）。

## 六、系统联系人（客服）预留位（用户 11:28 定；2026-10-24 已按后文状态激活）

用户要在好友里加客服：好友列表放一个系统联系人，用户点开就跟客服号聊天；客服号是对话的一方，站长用客服号收与回。最初本节只在数据/协议层占位；2026-10-24 已按 `forum-service-plan.md` 的客服一期口径激活：真实账号建号、聊天钥匙设置、固定常见问题上线，自动应答仍不做。

- **保留账号名 `qf-support`**（`friends-gate.js` 常量 `SUPPORT_ACCOUNT`）。名字带连字符、普通注册规则（只许字母数字）永远注册不到这个名，天然防冒名；正式启用时由站长通道建号（协调项：register-svc 的保留名单应同步加上它，归专项方案/一期处理，本轮未动注册服务文件）。
- **特殊对端类型 `system`**：`peerType()` 区分 `system`/`user`；`/chat/api/friends` 返回带类型的 `peers`（客服恒在首位）、`/chat/api/conversations` 每条带 `type`，客户端已能打「客服」标置顶渲染。
- **默认在列表**：`listFriends()` 对任何用户恒含客服号（客服号本人除外），不依赖 pairs 文件。
- **不可删**：用户↔客服号是**虚拟常驻关系**，不落 pairs；一期关系层实现删除/封禁联动时必须豁免本账号（已写入 `../README.md` 合并契约）。注意「不可删」指联系人与关系删不掉；某段对话记录的删除仍按第五节口径（那是记录，不是关系）。
- **闸口恒放行**：`areFriends(用户, 客服号)` 恒真，否则客服上线第一天就会被「非好友不能发」挡死。2026-10-24 激活后，客服号已存在并已设置聊天钥匙，生产真测中用户消息已成功送达并由客服端解开；激活前的 409 只属未建号阶段的历史行为。

**为什么不破 A 案**：客服号是一个**真实端点**——它有自己的身份钥匙，像普通用户一样在本端加解密。站长能看客服对话，是因为他**以客服号这个对话一方的身份**在端上收发（钥匙在他操作的端上），不是因为后台有任何窥视口：服务端与站长后台对客服对话同样只有密文，路由表面没有任何内容端点，这一点与普通对话完全一致。与 QFClash 的区别如实标注：QFClash 的「智能客服」是合成联系人且**明示非端到端加密**；这边的口径是客服号也走 A 案加密，不开明文例外。

**客服一期已定与已落地**：客服密码由系统生成强随机值，只存服务器 0600 配置文件，凭据交付由父代理走保险箱；客服号以普通聊天账号形态在网页端收发，不另建明文 inbox；固定常见问题 5 条已上线并标注待站长定稿；不做自动应答/工单化。多人值班时的钥匙共享方式仍未定，客服号在好友服务的 GUARD 名单内，好友关系层不会对它做删好友/共享联动。

## 八、设备包裹副本（2.3.0 L 线，2026-10-25 上线；其中「例外解锁页」口径已由第十节 O 线令废止，设备副本现为静默主序第②顺位与迁移源）

在密码包裹之外，新增「设备包裹副本」实现设备静默解锁：会话有效且本机持有设备密钥时，打开聊天直接解开记录，不再出现密码框；未勾记住账号密码时走本路径，勾住时密码材料路径（H 线）照常，两路并行互不依赖。

- **格式**：`keys[user].devices[deviceId] = {platform, wrappedPriv, wrappedVault, createdAt, updatedAt}`。副本包的是秘密原件本身（与密码无关，改密/rewrap 不影响其有效性）。两种包装 kind：`sodium-secretbox-v1`（壳/安卓：原始设备密钥经 crypto_secretbox 包装）、`webcrypto-aesgcm-v1`（网页：WebCrypto 不可导出密钥经 AES-GCM 包装，密钥存本机 IndexedDB）。壳侧设备密钥由主进程以 safeStorage（DPAPI）保护（接线补丁在 `../../v230/l-line/`，待总线合入 main.js）。
- **端点**（三端通用，platform ∈ shell/web/android）：`POST /chat/api/keys/device` 登记/更新、`GET /chat/api/keys/device/:deviceId` 取自己的副本、`POST /chat/api/keys/device/revoke` 撤销；`keys/setup` 可同批带 `device` 字段；`keys/me` 新增 `devices` 元数据清单（只有标识/平台/时间，不含密文）。上限 20 台/账号，服务端只做形态校验、只存密文。
- **迁移时机（静默）**：首次建钥匙同批登记；任何密码可得时刻（登录解锁、凭据静默解锁、例外解锁、恢复换包装成功后）在后台补写/更新；密码被重置但本设备有副本时，页面以副本自救并顺手用新密码重新包装。
- **例外**：新设备且无任何副本、且无已存凭据时，才显示正式「聊天加密解锁」页面（文案为官方正式表达，明示并非重新登录）；解锁成功即登记副本，第二次打开起静默。
- **自测**：`test-device.js` 20 项（核心往返、端点校验、撤销、他人不可取、数据文件无原件）全过；生产四场景审计全过（凭据路径/设备路径/新设备例外链/裸访问负例）。

## 九、桌面双栏（2.3.0 L2 线，2026-10-25，样图 d05 定版）

聊天页按页面内宽分两种形态，阈值 900px（CSS `@media (min-width:900px)` 与 JS `matchMedia` 同口径）：

- **双栏（≥900px）**：左会话列表 330px 常驻（搜索会话＋客服置顶＋官方标＋末条预览＋时间＋未读点＋当前会话高亮，客服 FAQ 仍在左栏下方），右会话区（头像/名称/副标题＋加密徽片＋消息区＋输入区）。点列表项只换右区会话，是页内视图变化：不整页导航、不写 history、页面长期保活不重载。
- **单栏（<900px，含手机 390）**：维持原「列表↔会话」切换与返回键回列表，与 m05 一致；会话打开时底部页签隐藏（由 body 状态类 `in-chat` 控制，原兄弟选择器随结构调整等义迁移）。
- **跨阈值不丢状态**：宽度变化只重排显示（`syncSplit`），不重拉数据、不重渲染消息、不清输入框——已打开会话、未发草稿、解锁状态（`state.priv/vaultKey/locked`）全部保留。
- **返回语义**：双栏无「返回列表」动作（返回键 CSS 隐藏、列表常驻）；单栏返回键清 `currentWith` 回列表。页面不做任何历史劫持，壳侧返回不依赖页面内部结构。
- **列表预览的加密口径**：预览只取本机已解密历史的末条（服务器只有密文、给不出预览）；未解锁或无历史时不显示预览，客服行回落样图副标题文案。未读点用服务端既有字段（会话 `lastSeq` > 我的 `myRead` 且非当前会话）。
- **硬约束不回退**：设备静默解锁全链（`qfChatState/qfShellDeviceUnlock/qfShellDeviceEnroll` 幂等、点开会话主动重试解锁、例外解锁页）、SSO/IP 还原、好友全链、改定文案、冻结令牌与既有呈现（气泡切角/加密徽片/骨架/按压反馈）均未改动语义，仅视图容器与列表行式扩展。

## 十、登录状态托管静默解锁（2.3.0 O 线，2026-10-25 站长令，覆盖此前一切解锁安排）

站长令钉死：任何端、任何入口打开聊天，永远不再出现输密码解锁页/解锁框；解锁凭登录状态静默完成；已加密的历史记录改后必须能正常打开；对外文案按新方式同步修订。本节为实现正本。

- **托管副本（sessionCopy）**：`keys[user].sessionCopy = {v:1, kind:'server-aesgcm-v1', iv, tag, cipher, updatedAt}`。明文为身份私钥原件＋保险库钥匙原件（JSON），由**服务端主密钥**以 AES-256-GCM 包裹。主密钥在服务器侧生成，存专用密钥文件（与数据文件同目录的 `session-master.key`，权限 600；可由配置 `sessionMasterKeyFile` 指定路径），只在服务进程内存中使用，值不进日志、不进数据文件、不出现在任何回报/文档中。格式带版本位（`v`）与算法标识（`kind`）以便将来轮换。
- **端点**（挂现行会话校验链，含 H 线 IP 还原；无会话一律 401）：`POST /chat/api/keys/session-copy` 上交钥匙原件由服务端包裹落存；`GET /chat/api/keys/session-copy` 仅凭本人有效会话取回本人钥匙原件（服务端在内存中解开后回传，客户端只在内存中持有）。`keys/setup` 可同批带 `sessionCopy` 字段；`keys/me` 新增 `hasSessionCopy`/`sessionCopyUpdatedAt` 元数据（不含材料）。`keys/setup` 的密码包裹改为与托管副本至少有其一（凭单点登录静默建钥匙时可无密码包裹，其后任一次密码可得时刻由客户端补写/重包）。
- **解锁顺序（钉死）**：打开聊天→会话有效→① sessionCopy 取回→② 设备包裹副本→③ 壳已存凭据（壳侧经 `qfShellUnlock` 递入）→全部失败显示正式「聊天暂时无法打开」提示（说明钥匙由登录状态保管、可联系官方客服），**页面不存在任何密码输入元素**。原「聊天加密解锁」页与「密码被改过」恢复页（`unlockView`/`recoverView`）已整体删除，`doUnlock/doRecover/doFreshStart` 一并移除；密码重置不再使记录作废——托管副本与密码无关。
- **静默迁移（保历史）**：客户端在任何一次成功解锁后（托管副本取回/设备副本/已存凭据/密码解开包裹），若账号尚无 sessionCopy，立即经已认证通道上交钥匙原件补写；新账号建钥匙时同批写 sessionCopy（经登录密码建钥匙时另带密码包裹与设备副本）。密码包裹与设备副本保留不删，作恢复与迁移源。站长本人账号的托管副本只能由其本人任一已装副本/凭据的客户端打开一次聊天自动完成，服务端无法代办。
- **对外表述**：钥匙由登录状态保管、登录了账号的设备可直接查看记录；不再使用「官方无法查看您的聊天内容」式严格端到端口径。消息与记录本身仍只以密文在本服务保存与中继，客服号仍为真实端点（第六节不变）。
