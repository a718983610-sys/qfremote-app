## 总结论

- **RC-03：不通过。** 核心问题：`k=8, n=2` 的 XOR 双校验**不能保证任意 2 个数据分片丢失可还原**；`repairPercent=5/20` 与固定 `k=8,n=2` 的实际开销也不自洽；`idr-request` 不能只做格式校验和“透传”，必须做限流、去重、鉴权绑定；FEC 分组与视频帧边界需在协议中显式定义。若明确降级为“只保证任意 1 丢可恢复，2 丢仅部分可恢复并触发恢复”，可转为**有条件通过**。
- **RC-09：有条件通过。** 方向合理，但“连续 2 次即降档”过于敏感；探针周期/判定窗口未定义；`pendingFrames` 客户端自报不可作为唯一背压依据；`drop-to-keyframe` 不应优先于 `reduce-fps`；手动升档需要滞回和冷却防乒乓；“档位切换即时不重连”对编码器偏好/分辨率等参数是错误假设。

# RC-03 评审

## 结论：不通过

必须改的点：

1. **明确 FEC 目标语义**：是“任意 2 丢可恢复”还是“任意 1 丢可恢复 + 2 丢可判定不可恢复”。当前 `k=8,n=2` 不能宣称任意 2 丢可恢复。
2. 若坚持任意 2 丢可恢复，改用 **RS over GF(256) 且 m>=2**，或纯 XOR 下把校验分片数提高到 `n>=4`，但后者开销 50% 不推荐。
3. `repairPercent` 必须定义分母、最小校验分片数、实际开销，并允许 `k/m` 随档位变化；FEC 参数只能在关键帧/块边界切换。
4. `idr-request` 必须服务端准入控制：会话绑定、鉴权、限流、合并、防重放、审计。
5. FEC 块边界必须定义：不得跨关键帧，跨帧聚合必须携带帧元数据；不可恢复时明确丢帧和 IDR 请求语义。
6. 验收从“5% 随机丢包”扩展为确定性丢包 trace，至少覆盖突发丢包、连续 2 丢、关键帧丢、尾块、乱序、块头丢失。

## (1) XOR 双校验构造是否成立

**不成立。** 设第 `i` 个数据分片参与的校验列向量为 `c_i ∈ GF(2)^n`，表示它参与哪些校验分片。丢失集合可恢复的充要条件是这些丢失分片对应的列向量在 GF(2) 上线性无关。

当 `n=2` 时，非零列向量只有 3 种：

- `(1,0)`
- `(0,1)`
- `(1,1)`

要保证任意 2 个数据分片丢失都可恢复，需要所有数据分片的列向量**非零且两两不同**。因此最多只能有 3 个数据分片，即 `k<=3`。`k=8` 必然有重复列，某些双丢组合不可恢复。

补充：
- 任意 1 丢可恢复的条件是每个数据分片的列向量非零，即每个数据分片至少参与一个校验。
- 如果接收端通过序号知道哪些分片丢失，则“能否恢复”是可判定的：两丢失列相同则不可恢复，不同则双 XOR 可恢复。
- 如果丢失位置未知，双 XOR 不能保证检测所有 2 个错误。

### 最小正确构造建议

**推荐方案：RS over GF(256)。**

- 若要求任意 2 丢可恢复：`m=2` 个校验分片即可，例如 `k=10,m=2`，开销 20%；低档可用 `k=20,m=1`，开销 5%，但只能保证任意 1 丢。
- JS 参考实现复杂度：GF(256) 查表，编码每块约 `O(k*m*L)`，`L` 为分片长度；解码 erasure 时解 `m×m` 线性方程，`m=2` 可手写，实际开销可控。
- 对 1KB 分片、30fps、`k=20,m=1` 的场景，纯 JS 参考实现可承受，但需做 TypedArray 和查表优化，并给出 CPU 基准。

**若接受降级语义：**

`k=8,n=2` 可明确为：
- 任意 1 丢：100% 恢复；
- 任意 2 丢：仅当两丢失分片所在校验列不同才可恢复；
- 对 8 个数据分片做 3 组非零列分配，例如 3/3/2，双丢可恢复对为 `C(8,2)-(C(3,2)+C(3,2)+C(2,2))=21/28≈75%`；
- 不可恢复块标记为 FEC block lost，触发一次受控的 `idr-request` 或上层恢复。

这个降级语义必须写入验收口径，不能写成“2 丢可还原”。

## (2) idr-request 是否需要服务端限流/鉴权

**必须。** 关键帧通常远大于普通帧，编码器成本高。恶意或异常高频 IDR 请求会造成关键帧风暴、码率突增、编码器排队，反而加剧拥塞。

建议语义与数值：

- **鉴权/绑定**：只接受已登录且已绑定该 `sessionId` 的控制通道；服务端校验 `sessionId` 属于当前连接/用户/agent；禁止客户端指定任意 `sessionId`。
- **字段校验**：`reason` 白名单；`seq` 每会话单调递增，服务端维护重放窗口；`atTs` 仅用于日志，服务端使用接收时间做调度。
- **限流**：
  - 每 session 令牌桶：`rate=0.5/s`，`burst=2`；
  - 同 reason 合并窗口：`loss` 1s，`quality-change` 2s；
  - 硬上限：每 session `1/s`，`5/10s`；
  - 每 agent 令牌桶：`rate=2/s`，`burst=5`；
  - 超限返回 `idr-request-result: rejected/coalesced`，记录原因；连续超限触发 10s 冷却和告警。
- **特殊放行**：新订阅/join 在会话建立后 10s 内允许 1 次；`quality-change` 每次档位切换最多 1 次。
- **执行语义**：服务端不是纯透传，而是“校验 + 鉴权 + 去重 + 限流 + 转发/合并 + 审计”。同一会话多观看端请求需按 session 合并，不能每个观看端各触发一次关键帧。

## (3) FEC 分组与视频帧边界

必须明确：

- **FEC 块不得跨关键帧边界。** 关键帧必须独立成块，避免关键帧丢失污染后续非关键帧。
- 推荐**每帧一个 FEC 块**；若为小帧聚合，最多聚合少量非关键帧，且块头必须携带：
  - `blockId`、`symbolIndex`、`symbolCount`
  - `frameId`、`frameStart/frameEnd`、`isKeyframe`
  - `sliceIndex/sliceCount`
  - `symbolLength`、`lastSymbolPadding`
- 跨帧时丢包处理：接收端根据块元数据判定该块覆盖的帧；若块不可恢复，不能输出参考链不完整的帧，应丢弃/冻结受影响帧并触发一次受控 `idr-request`。
- 尾块必须零填充并保留真实长度，否则 XOR/RS 分片长度不一致会解码错误。
- 不可恢复判定不要“一丢即请求”，建议超时窗口 `RTT + jitter + 1 帧`，并允许乱序重排窗口。
- 档位切换时 FEC 参数只能在关键帧或块边界生效；块头需带 FEC 参数版本，避免收发端 k/m 不一致。

## (4) 沙箱验收是否合理

**用 5% 随机丢包模拟不够。** 随机独立丢包无法覆盖远程桌面最常见的突发丢包、参考链断裂和关键帧丢失。

更好口径：

- 丢包 trace：均匀 5%；Gilbert-Elliott 突发模型，平均 5%，burst 长度 1/2/5/10；固定丢关键帧、尾块、连续 2 丢、块头、乱序、重复、延迟抖动。
- 指标：
  - 单丢恢复率、双丢恢复率/可恢复概率；
  - 帧可解码率；
  - `idr-request` 次数/秒、关键帧间隔；
  - 恢复时间 p50/p95/p99，同时报毫秒和帧数；
  - 实际 FEC 开销、CPU/内存；
  - 误判“不可恢复”率。
- “自愈时间”定义：从丢包注入到第一个完整可解码帧可输出的时间；模拟帧数必须绑定固定帧率并同时报 ms，否则不可比较。
- 参考实现需加属性测试：随机数据、随机 erasure、尾块、长度不等、连续丢。

# RC-09 评审

## 结论：有条件通过

必须改的点：

1. 不要“连续 2 次变差即降档”，改为双阈值 + 时间窗口 + 滑动样本 + 冷却。
2. 明确探针上报周期和服务端判定窗口；`lossPct` 必须有采样包数和统计窗口，避免小样本噪声。
3. `pendingFrames` 只能作为提示，不能单独触发背压；需服务端独立可观测信号或至少多信号交叉验证。
4. 背压优先级改为 `reduce-fps` 优先，`drop-to-keyframe` 作为二级/严重状态手段，并与 IDR 限流合并。
5. 手动升档必须做健康窗口检查、升档冷却和快速回退次数限制，防乒乓。
6. “档位切换即时不重连”需拆分热可调与需重建编码器的参数；编码器偏好、分辨率缩放切换至少需关键帧/编码器重配，不能假设完全无感。

## (1) 连续 2 次即降档是否过于敏感

**是。** 尤其使用 `rtt>300 或 loss>5` 的“或”条件时，一次瞬时尖峰加一次样本就会降档，容易误降。

建议值：

- 正常探针周期 1s；弱网或档位切换后 10s 内 500ms；页面隐藏降为 5s。
- 服务端使用滑动窗口：
  - 一般坏条件：`rtt>300ms` 或 `loss>5%` 或 `jitter>50ms`，5s 窗口内至少 3 个样本满足，且持续 >=3s 才降档；
  - 严重坏条件：`rtt>800ms` 或 `loss>20%` 或 `decodeLag>500ms`，连续 2 个样本即可降档；
  - 对 rtt/loss 使用中位数或 EWMA，`α≈0.3`，避免单点尖峰。
- 降档冷却：每次降档后至少保持 5s；连续恶化时每 3s 最多降一档；但允许弱网下逐级降到 smooth。
- 恢复不自动升档；手动升档健康条件建议：`rtt<150ms`、`loss<1%`、`jitter<30ms`、`decodeLag<150ms`，持续 20s。降档阈值与升档阈值分离形成滞回。

## (2) 探针周期与判定窗口推荐值

- 客户端上报周期：正常 1s；弱网/切换后 500ms，持续 10s；隐藏页 5s。
- 服务端判定窗口：
  - 短窗 3 个样本，用于严重坏快速降档；
  - 长窗 5 个样本/5s，用于一般坏确认；
  - 统计窗口 10s，用于日志、趋势和防抖。
- `lossPct` 必须声明统计窗口和最小包数，例如 1s 窗口且至少 50 个包，否则低包率下 5% 指标噪声很大；区分上行/下行丢包，不能只报一个混合值。

## (3) 背压信号优先级

**`reduce-fps` 应优先于 `drop-to-keyframe`。**

理由：
- 关键帧通常更大，`drop-to-keyframe` 若同时请求新关键帧，会加剧带宽拥塞；
- 远程桌面实时性优先，先降生产速率可平滑降低队列和解码压力；
- `drop-to-keyframe` 更适合参考链已损坏、花屏、队列中非关键帧依赖失效、严重积压需要快速清空的情况。

建议分级：
- L1：`reduce-fps`，例如降到 15/10fps，同时档位建议降一档；
- L2：降分辨率/码率；
- L3：`drop-to-keyframe` + 受控 IDR 请求，且 IDR 请求纳入 RC-03 限流。

`drop-to-keyframe` 语义应改为“丢弃直到关键帧，并可选请求关键帧”，避免等待现有远期关键帧造成长时间冻结。执行主体、ACK、幂等、超时需定义。

## (4) 手动升档后立刻又降档的乒乓

处理建议：

- 手动升档前必须检查健康窗口：`rtt<150ms、loss<1%、jitter<30ms、decodeLag<150ms` 持续 20s，否则拒绝升档并提示原因。
- 只允许一次升一档；升档后设置观察窗：严重坏立即降；一般坏需 3s 窗口确认后再降。
- 冷却：升档后 10s 内不因旧样本降档，但严重坏可立即降。
- 同一目标档在 60s 内发生 2 次“手动升档后 10s 内被降回”，则对该目标档冷却 60s，并记录用户意图与网络不满足原因。
- 降档阈值和升档阈值必须分离，形成迟滞，避免边界抖动。

## (5) pendingFrames 是否可信，服务端独立信号

**客户端自报不可信**，只能作为提示。恶意或异常客户端可虚报 `pendingFrames/decodeLagMs` 迫使服务端降档。

服务端应至少使用以下独立信号之一或组合：
- 若媒体路径经过 Node 服务：WebSocket/Node socket `bufferedAmount`、outbound queue bytes、drain 等待时间、写阻塞、发送速率；
- 每 session 的发送队列高水位、帧发送间隔、关键帧请求频率；
- 接收端 ACK/解码完成序号（若协议有）；
- agent 侧发送队列/编码器队列（若可获得）；
- 客户端上报值的范围校验、变化率校验、与 `decodeLagMs` 交叉验证。

建议背压决策至少满足：服务端独立指标高 + 客户端上报高，或连续 3 个样本异常；单字段不能直接触发降档。对异常上报降权并记录。

## RC-09 其他必须补充的边界

- 档位参数分“热可调”和“需重建”：
  - 热可调：目标码率、帧率上限、FEC repairPercent 在关键帧/块边界切换；
  - 需关键帧/编码器重配：分辨率缩放、编码器偏好。切换时触发 IDR，接收端清旧参考帧；不能宣称全部即时无感。
- `config.json` 需 schema 校验、版本、默认回退、原子热加载、每会话参数快照；未知档位回退默认并告警。
- `downgrade-to` 需定义客户端是否必须执行、ACK 语义和超时；否则“验收一路降到 smooth”不可验证。
- 验收沙箱除探针序列外，还要注入探针丢失、乱序、重复、时钟偏移、恶意上报、配置热加载、编码器偏好切换、背压执行 ACK。真机门禁建议明确：300ms RTT + 5% 丢包下不断连、10s 内到 smooth、关键帧请求不超过 `1/s` 或 `5/10s`、恢复后不自动升档、无档位乒乓。
